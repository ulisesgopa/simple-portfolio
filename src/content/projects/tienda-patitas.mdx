## Overview

**Tienda Patitas** is a complete e-commerce system for a pet products retailer. It runs as three independent services: a public storefront where customers browse and buy, a backend API that handles all business logic and data, and an admin dashboard that gives the business owner and cashiers full control over the operation.

---

## Role
**Solo Developer**: backend API, public storefront, and admin dashboard — all three services from schema design to production deployment.

---

## The Problem

The client ran an active pet products business with no digital infrastructure beyond social media. Orders came through WhatsApp, inventory lived in a spreadsheet, and there was no way to track sales performance, manage customers, or process payments systematically. The goal was a real system: customers shop online, the owner manages everything from one dashboard, and a cashier can process counter sales with a POS.

---

## Three Services

### 1. Backend API

| Layer | Technology |
|-------|-----------|
| Runtime | Bun |
| Language | TypeScript |
| HTTP | Bun.serve |
| Database | PostgreSQL |
| ORM | Prisma |
| Auth | JWT via jose (access 15min + refresh 7d) |
| Payments | MercadoPago (checkout + webhooks) |
| Email | Resend (order confirmations, receipts) |
| File storage | Vercel Blob (product images) |
| Error tracking | Sentry |
| Logging | Pino (structured logs) |
| API Docs | OpenAPI + Swagger at `/docs` |

**Modules:** auth, products, categories, customers, sales, purchases, cash register, discount codes, business config, payments, health check.

**Key data model decisions:**
- `PaymentMethod` enum: CASH, TRANSFER, CARD, MERCADOPAGO — a single sale can mix payment methods
- `SaleSource` enum: POS, STORE, APP — every sale is attributed to its origin channel
- `OrderStatus` and `PaymentStatus` as separate states — a sale can be delivered but partially paid

### 2. Public Storefront

| Layer | Technology |
|-------|-----------|
| Build tool | Vite |
| Framework | React |
| Language | TypeScript |
| UI | shadcn/ui + Radix UI |
| Styling | TailwindCSS |
| Routing | React Router |
| Server state | TanStack Query |
| Forms | React Hook Form + Zod |
| Auth | JWT with automatic token refresh |
| Analytics | Vercel Analytics + Speed Insights |
| Testing | Vitest + Testing Library |

**Customer-facing features:**
- Product catalog with category filtering (client-side, instant)
- Product detail pages with images, nutritional info, sizes, and benefits
- Customer account: registration, login, order history
- MercadoPago checkout integration
- WhatsApp conversion fallback: product details encoded into a deep link for one-tap purchase inquiry
- Discount code validation at checkout

### 3. Admin Dashboard + POS

| Layer | Technology |
|-------|-----------|
| Build tool | Vite |
| Framework | React |
| Language | TypeScript |
| UI | shadcn/ui + Radix UI |
| Styling | TailwindCSS |
| Routing | React Router |
| Server state | TanStack Query |
| Local state | Zustand |
| Forms | React Hook Form + Zod |
| Animations | Framer Motion |
| Testing | Vitest |

**Admin modules:**
- **POS**: counter sales with mixed payment methods (cash, transfer, card, MercadoPago), cash register sessions (open/close), change calculation
- **Products**: full CRUD with images (Vercel Blob), sizes, nutritional info, benefit tags, categories, stock tracking
- **Customers**: customer profiles with purchase history and balance
- **Sales**: sale history with source tracking, payment status, order status, and delivery management
- **Purchases**: supplier purchase management and inventory updates
- **Discount codes**: create and manage promotional codes with validation rules
- **Company settings**: business profile and configuration

## Final Thoughts

Tienda Patitas is the most architecturally complete project in the freelance section of this portfolio. Owning the entire system — backend API, storefront, and admin — across a real retail domain forced every decision about data modeling, payment flows, and API contracts to be thought through to production level. There's no "the backend team will handle that" here: if the payment webhook fires twice, that's my problem. If stock goes negative after a race condition, that's my problem. That accountability shapes how the system was designed.
